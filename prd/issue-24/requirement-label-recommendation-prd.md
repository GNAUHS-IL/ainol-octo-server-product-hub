# PRD：需求单标签推荐能力

## 1. 背景与问题

Issue #24 反馈：用户在创建需求单时，经常不确定应该选择哪些标签，导致后续筛选、归类和统计不够准确。用户希望系统能根据需求标题和描述推荐相关标签，并在用户确认后再写入需求单，降低人工选择标签的成本和误差。

现有源码与文档显示，Octo 已有需求/缺陷提交模板、标签归类自动化、产品领域规则索引、用户输入边界、权限隔离、限流、用户可见错误和审计脱敏要求。本 PRD 仅定义“需求单标签推荐”的用户可见流程、推荐边界、确认/取消/调整、失败提示、权限与风险口径，不定义内部实现方式。

- Feature 模板要求用户填写问题动机、期望方案和相关组件，说明创建需求单时已有结构化信息可用于用户理解和归类。来源: .github/ISSUE_TEMPLATE/feature_request.yml#L9-L16；来源: .github/ISSUE_TEMPLATE/feature_request.yml#L17-L24；来源: .github/ISSUE_TEMPLATE/feature_request.yml#L32-L45
- Bug 模板要求用户填写描述、复现、期望、实际、组件和严重程度，说明需求/缺陷材料天然对应多维归类。来源: .github/ISSUE_TEMPLATE/bug_report.yml#L9-L16；来源: .github/ISSUE_TEMPLATE/bug_report.yml#L17-L28；来源: .github/ISSUE_TEMPLATE/bug_report.yml#L29-L42；来源: .github/ISSUE_TEMPLATE/bug_report.yml#L50-L63；来源: .github/ISSUE_TEMPLATE/bug_report.yml#L64-L74
- Release Drafter 以标签区分 Feature、Bug Fix、CI/Infrastructure、Documentation 等变更类别，说明标签会影响后续归类和发布整理。来源: .github/release-drafter.yml#L10-L19
- PR Labeler 工作流说明标签自动化会调用 GitHub API 设置标签和评论，并强调不执行外部分支内容，说明标签自动化需要受安全边界约束。来源: .github/workflows/labeler.yml#L3-L11；来源: .github/workflows/labeler.yml#L18-L28
- 规则索引列出 Space 隔离、用户可见错误、限流、测试和提交风格等知识领域，可作为推荐候选标签或推荐理由的领域依据。来源: .octospec/index.md#L9-L15
- 用户输入边界已有长度、范围、页大小、游标等校验要求，说明基于标题和描述触发推荐时也需要输入范围与无效输入提示。来源: modules/messages_search/validate.go#L11-L18；来源: modules/messages_search/validate.go#L88-L99；来源: modules/messages_search/validate.go#L147-L160；来源: modules/messages_search/validate.go#L170-L184
- Space 隔离规则要求访问用户数据必须执行隔离和 ownership 检查，读写不得跨 Space。来源: .octospec/rules/space-isolation.md#L21-L31；来源: .octospec/rules/space-isolation.md#L34-L37
- 用户可见错误规则要求面向用户的错误走本地化错误口径，避免原始错误直接暴露。来源: .octospec/rules/error-handling.md#L19-L29；来源: .octospec/rules/error-handling.md#L31-L34

## 2. 目标与非目标

### 目标

- 在用户创建需求单时，根据标题和描述展示候选标签推荐。
- 推荐标签覆盖常见产品领域，例如消息链路、群聊、Thread、权限、通知、性能、后台管理、Bot 与 Agent 等。
- 用户可以查看推荐理由或推荐依据摘要，并选择接受、取消、调整或手动补充标签。
- 只有用户明确确认后的标签才写入需求单；未确认时不得自动改变需求单标签。
- 推荐不足、无法判断或存在低置信度时，明确提示用户手动选择，而不是强行写入不确定标签。
- 对推荐准确性边界、权限可见性、敏感内容脱敏、频率限制、失败提示和审计追溯建立统一产品口径。

### 非目标

- 不替产品运营负责人最终裁定需求类型、优先级、状态或是否 accepted / blocked / duplicate / wontfix / invalid。
- 不强制所有推荐标签自动写入，也不要求用户必须接受推荐。
- 不改变现有需求单创建、分诊、PRD、Review 和状态闭环规则。
- 不要求推荐覆盖所有历史需求单；历史需求可保留现有标签或由有权人员另行整理。
- 不定义内部落地方案、研发结构、模型选择、部署方案或具体技术字段。
- 不在推荐理由、通知、评论、日志或审计中明文展示 token、cookie、secret、私钥、生产凭证、客户隐私或无权内容。

## 3. 用户故事

### US-01：普通用户创建需求单时获得标签建议
- 角色：作为群内反馈人或需求提交人
- 场景：当我填写需求标题和描述，但不确定应该选择哪些标签
- 诉求：希望系统展示一组候选标签和简短推荐依据
- 价值：以便我更快完成需求单创建，并减少误选或漏选标签
- 来源: .github/ISSUE_TEMPLATE/feature_request.yml#L9-L16；来源: .github/ISSUE_TEMPLATE/feature_request.yml#L17-L24；来源: .github/ISSUE_TEMPLATE/feature_request.yml#L32-L45

### US-02：用户确认后才写入标签
- 角色：作为需求提交人或编辑人
- 场景：当系统给出推荐标签后，我需要决定是否采纳
- 诉求：希望可以接受全部推荐、取消部分推荐、手动补充或完全跳过推荐
- 价值：以便最终标签反映我的真实意图，避免系统误改需求单

### US-03：产品运营负责人减少后续补标签成本

- 场景：当大量需求单进入需求池，需要筛选、归类、统计和后续发布整理
- 诉求：希望初始标签更准确，并能看到低置信度或待确认标签
- 价值：以便减少人工补标签、改标签和后续统计偏差

- 场景：当标题/描述信息不足、内容含糊、跨多个领域或推荐结果冲突
- 诉求：希望系统明确提示无法可靠推荐，并允许继续手动选择
- 价值：以便避免错误标签被强行写入，保持需求状态和标签真实性

- 场景：当标签推荐、确认、取消或写入出现争议、异常或疑似滥用

## 4. 功能需求

### F-01-1 创建时展示候选标签推荐
- 所属故事：US-01、US-03
- 需求描述：用户填写需求标题和描述后，系统应展示一组候选标签推荐，并标明标签名称、类别和简短推荐依据。
- 业务规则：推荐标签应来自当前可用标签体系或产品运营负责人认可的候选范围；推荐结果应区分类型、优先级、状态和领域等不同标签类别，避免混淆。
- 边界场景：标题或描述为空、信息过短、内容含糊、跨多个领域、存在多个可能标签或推荐结果不足时，应提示用户补充信息或手动选择。
- 来源: .github/ISSUE_TEMPLATE/feature_request.yml#L9-L16；来源: .github/ISSUE_TEMPLATE/feature_request.yml#L17-L24；来源: .github/ISSUE_TEMPLATE/bug_report.yml#L50-L63；来源: .octospec/index.md#L9-L15

### F-01-2 推荐依据摘要
- 所属故事：US-01、US-03、US-04
- 需求描述：每个推荐标签应提供用户可理解的依据摘要，例如命中的主题、组件、问题类型或用户描述中的关键信息。
- 业务规则：依据摘要只说明可见、必要、脱敏后的判断理由；不得复述敏感信息、无权内容或完整私密正文。
- 边界场景：依据不足、依据冲突、内容疑似敏感或系统无法解释推荐原因时，应展示“依据不足 / 需人工确认”等安全提示。
- 来源: .octospec/rules/error-handling.md#L19-L29；来源: modules/messages_search/audit.go#L12-L24；来源: modules/messages_search/audit.go#L62-L70

### F-01-3 用户确认、取消和调整
- 所属故事：US-02
- 需求描述：用户应能接受全部推荐、取消部分推荐、手动补充其他标签或跳过推荐。
- 业务规则：只有用户明确确认后的标签才写入需求单；未确认、已取消或低置信度未确认的标签不得自动写入。
- 边界场景：用户关闭页面、重复点击、推荐结果过期、多人同时编辑、用户权限变化或标签候选已失效时，应保持需求单标签不被误改，并提示当前真实状态。
- 来源: .github/workflows/labeler.yml#L3-L11；来源: .github/workflows/labeler.yml#L18-L28

### F-01-4 低置信度和无法判断提示
- 所属故事：US-04
- 需求描述：当系统无法可靠推荐标签，或推荐结果互相冲突时，应明确提示用户手动选择或补充描述。
- 业务规则：不得为了填满标签而强行推荐；低置信度标签应以待确认状态呈现，不得默认写入。
- 边界场景：标题过短、描述缺失、同时涉及多个领域、文本含反讽或否定、仅包含截图/附件、内容语言混杂时，应安全降级。
- 来源: modules/messages_search/validate.go#L11-L18；来源: modules/messages_search/validate.go#L170-L184；来源: .octospec/rules/error-handling.md#L31-L34

### F-01-5 标签类别边界
- 所属故事：US-01、US-03
- 需求描述：推荐结果应清晰区分标签类别，例如 type、priority、status、area 等，并说明哪些标签可由用户选择，哪些需要产品运营负责人确认。
- 业务规则：涉及优先级、最终状态、blocked、duplicate、wontfix、invalid 等可能影响仲裁的标签时，应优先展示为建议或待确认，不越权自动裁定。
- 边界场景：用户选择的标签与产品运营负责人分诊冲突、推荐标签与当前状态冲突、多个状态标签并存或标签体系变更时，应提示以产品运营负责人和当前远端事实为准。
- 来源: .github/release-drafter.yml#L10-L19；来源: .octospec/index.md#L9-L15

### F-01-6 权限与可见性过滤
- 所属故事：US-02、US-05
- 需求描述：标签推荐、推荐依据、可选标签范围和写入结果必须按当前用户权限展示和处理。
- 业务规则：不得基于用户无权查看的需求、评论、附件、群聊、Thread、Bot 或跨 Space 内容给出可反推详情的推荐理由；无权时应安全提示而非泄露对象是否存在。
- 边界场景：用户跨 Space 创建、从群聊/Thread 创建、权限变化、退群、需求迁移或来源对象失效时，应按当前可见性安全降级。
- 来源: .octospec/rules/space-isolation.md#L21-L31；来源: .octospec/rules/space-isolation.md#L34-L37

### F-01-7 敏感内容脱敏
- 所属故事：US-04、US-05
- 需求描述：标题、描述、推荐依据、用户调整内容或审计摘要中包含疑似敏感信息时，应脱敏、截断或提示人工确认。
- 业务规则：疑似 token、cookie、secret、私钥、生产凭证、客户隐私、内部敏感链接或私密消息全文不得出现在推荐理由、公开评论、群通知或审计明文中。
- 边界场景：敏感信息出现在附件、截图、长文本、链接或用户复制的日志片段中时，应优先安全降级，不硬推公开展示。
- 来源: .github/ISSUE_TEMPLATE/bug_report.yml#L92-L98；来源: modules/messages_search/audit.go#L12-L24；来源: modules/messages_search/audit.go#L62-L70

### F-01-8 频率与范围控制
- 所属故事：US-01、US-05
- 需求描述：标签推荐、重新推荐、批量编辑和重复确认应有频率、文本长度和操作范围边界。
- 业务规则：推荐能力不得被用于高频探测标签体系、批量分析无关内容、绕过权限或造成服务压力；触发限制时应展示用户可理解提示。
- 边界场景：用户频繁修改标题/描述、连续点击重新推荐、多人同时编辑、批量创建需求或异常失败重试时，应降噪、限制或建议稍后重试。
- 来源: modules/messages_search/validate.go#L11-L18；来源: modules/messages_search/validate.go#L147-L160；来源: .octospec/rules/rate-limit.md#L19-L29

### F-01-9 标签写入结果展示
- 所属故事：US-02、US-03
- 需求描述：用户确认后，应能看到最终写入的标签列表、未采纳标签和需要人工确认的标签状态。
- 业务规则：写入结果应与需求单列表筛选、详情页展示和后续统计口径一致；不得把“推荐成功”误表达为“标签已写入”。
- 边界场景：部分标签写入失败、标签已被移除、标签名变化、多人编辑冲突或远端状态已更新时，应提示当前真实结果和可恢复操作。
- 来源: .github/release-drafter.yml#L10-L19；来源: .octospec/rules/error-handling.md#L19-L29

### F-01-10 审计与追溯摘要
- 所属故事：US-05
- 需求描述：推荐触发、推荐结果展示、用户确认/取消/调整、写入结果、失败和频控应保留可追溯安全摘要。
- 业务规则：审计摘要应说明操作者、需求单范围、推荐标签类别、用户确认结果和处理时间；不得记录明文敏感内容、完整标题/描述或无权对象详情。
- 边界场景：推荐争议、误标签、权限变化、疑似滥用、敏感内容脱敏或用户申诉时，应能基于安全摘要排查。

## 5. 状态与提示

- 待推荐：用户已填写可用于推荐的标题或描述，系统可尝试给出候选标签。
- 推荐中：系统正在生成候选标签，请稍后查看结果。
- 推荐完成：已生成候选标签，等待用户确认、取消或调整。
- 低置信度：推荐依据不足或存在冲突，建议用户手动选择或补充描述。
- 无法推荐：当前信息不足、格式不支持或推荐能力暂不可用，用户可继续手动选择标签。
- 待用户确认：候选标签尚未写入需求单。
- 已确认写入：用户确认后的标签已写入需求单。
- 部分写入：部分标签因权限、失效、冲突或远端状态变化未写入。
- 已取消推荐：用户取消本次推荐，不改变需求单标签。
- 需人工确认：涉及优先级、最终状态、冲突标签、敏感内容或越权风险，需要产品运营负责人确认。
- 操作过于频繁：推荐或确认触发频率限制，请稍后重试。
- 疑似敏感内容：推荐依据或展示内容已脱敏、截断或需人工确认。

## 6. 验收标准

- AC-01：当用户填写需求标题和描述后，能看到一组候选标签及可理解的推荐依据摘要。
- AC-02：用户可以接受全部推荐、取消部分推荐、手动补充其他标签或跳过推荐。
- AC-03：只有用户明确确认后的标签会写入需求单；未确认、已取消或低置信度未确认的标签不会自动写入。
- AC-04：当系统无法可靠推荐时，用户能看到明确提示，并可继续手动选择标签或补充描述。
- AC-05：推荐结果能区分 type、priority、status、area 等标签类别；涉及最终状态、优先级或异常结论的标签不越权自动裁定。
- AC-06：需求单创建完成后，列表筛选、详情页展示和统计使用的是用户最终确认后的标签。
- AC-07：当用户无权查看相关来源内容时，推荐依据、候选范围和错误提示不泄露无权对象、私密评论、附件或跨 Space / 群 / Thread / Bot 信息。
- AC-08：当标题、描述、推荐依据或用户补充内容包含疑似 token、cookie、secret、私钥、生产凭证、客户隐私或内部敏感链接时，推荐展示、通知和审计仅展示脱敏摘要或人工确认提示。
- AC-09：当推荐、重新推荐、确认或批量编辑过于频繁时，系统有频率和范围边界，并展示可理解提示。
- AC-10：当标签写入部分失败、标签候选失效、多人编辑冲突或远端状态变化时，用户能看到当前真实结果和可恢复操作。
- AC-11：运营或需求管理人员能基于安全摘要追溯推荐、确认、取消、调整、写入、失败和频控结果；审计不记录明文敏感内容或无权对象详情。
- AC-12：产品说明覆盖推荐触发条件、候选范围、推荐理由、用户确认、取消/调整、低置信度处理、权限过滤、脱敏、限流、失败提示和审计口径。

## 9. 五类风险检查

- 多租户 / Space 隔离：推荐依据、候选范围和写入结果必须按当前用户可见内容生成和展示；不得通过推荐理由或缺失提示泄露跨 Space / 群 / Thread / Bot 信息。
- 权限 / ownership：用户只能确认自己有权处理的需求标签；涉及优先级、最终状态和异常结论的标签不越权自动裁定，需产品运营负责人 Review 或确认。
- 安全 / 外部输入 / 凭证：标题、描述、附件、日志片段和推荐依据可能含敏感信息；疑似 token、cookie、secret、私钥、生产凭证、客户隐私或内部敏感链接必须脱敏、截断或人工确认。
- 限流 / 防滥用：推荐、重新推荐、批量编辑和确认写入需要频率、文本长度和范围边界，避免高频探测、批量分析无关内容或造成服务压力。
- 审计 / 可追溯：关键动作需记录安全摘要，包括操作者、需求范围、推荐标签类别、用户确认结果、失败原因类别和处理时间；审计不得记录明文敏感内容、完整标题/描述或无权对象详情。
