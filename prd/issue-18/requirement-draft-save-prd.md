# PRD：需求单草稿保存能力

## 1. 背景与问题

Issue #18 反馈：群内用户在描述普通需求时，信息经常尚未整理完整；如果立即正式提交，容易缺少标题、背景、期望效果、优先级、截图或消息链接等关键信息；如果不提交，又容易遗忘或丢失上下文。因此希望 Octo Server 支持“需求单草稿保存”能力，让需求先沉淀为草稿，后续补齐后再正式提交。

现有源码显示，Octo 已具备群聊、Bot、Thread、文件上传、消息搜索、Bot 事件读取和 App Bot 管理等与需求收集体验相关的基础能力；但本需求不是要求直接改变这些既有能力，而是定义“需求单草稿”作为用户可见产品能力时，需要呈现哪些信息、哪些状态、哪些权限与安全边界。

- Bot API 已在统一 Bot 鉴权与业务限流下提供发送消息、事件读取、群、Thread 等能力。来源: modules/bot_api/bot_api.go#L400-L413；来源: modules/bot_api/bot_api.go#L423-L435
- Bot 发送消息要求目标会话、会话类型和内容有效。来源: modules/bot_api/send.go#L36-L48；来源: modules/bot_api/send.go#L53-L60；来源: modules/bot_api/send.go#L60-L70
- Bot 事件读取结果包含事件、消息编号、发送人、会话、时间和内容等上下文信息。来源: modules/bot_api/events.go#L37-L51
- 群与 Thread 已有用户可见的群、成员、GROUP.md、Thread、THREAD.md 等协作入口。来源: modules/group/api.go#L98-L112；来源: modules/group/api.go#L118-L132；来源: modules/thread/api.go#L181-L195
- 创建 Thread 时已经存在来源消息编号与来源消息内容摘要的用户可见概念，可作为“消息链接/来源上下文”类产品口径的参考。来源: modules/thread/api.go#L221-L225；来源: modules/thread/api.go#L232-L246；来源: modules/thread/api.go#L251-L258
- 文件模块已有认证上传、预签名上传、下载 URL 等文件能力，同时源码明确提示下载 URL 的对象保密仍需谨慎对待。来源: modules/file/api.go#L83-L92；来源: modules/file/api.go#L93-L98；来源: modules/file/api.go#L101-L109；来源: modules/file/api.go#L111-L117；来源: modules/file/api.go#L118-L130

## 2. 目标与非目标

### 目标

- 支持群内提问用户或有权限运营人员创建需求单草稿，在信息未齐全时先保存需求线索。
- 草稿可保存用户可见信息项：标题、背景、期望效果、优先级建议、相关截图、相关文件、来源消息链接或消息引用、补充说明。
- 草稿与正式需求单必须有清晰状态区分，避免草稿被误认为已进入正式处理或验收流程。
- 支持草稿后续补齐、预览、正式提交、取消或删除，并给出明确成功/失败提示。
- 支持对草稿的权限、可见性、附件/消息链接范围、安全脱敏、限流和审计口径做产品化约束。
- 让 Octo 产品运营负责人、需求管理专员和反馈人能用一致口径判断：草稿是否已保存、缺什么、谁能看、何时可正式提交。

### 非目标

- 不改变现有需求池最终分诊权、优先级最终裁定权和状态仲裁权。
- 不把草稿等同于正式 GitHub issue、正式 PRD 或已接受需求。
- 不承诺自动补齐所有需求信息；系统只提示缺口，仍需用户或运营人员确认。
- 不提供跨 Space、跨群、跨 Bot 的草稿全量浏览或导出入口。
- 不绕过现有群、Thread、文件、消息、Bot 与 Space 的权限边界。
- 不展示或保存 token、cookie、secret、私钥、内部错误堆栈或无权对象详情。
- 不定义内部实现路径、服务端方案、内部技术细节或部署方案。

## 3. 用户故事

### US-01：群内反馈人保存未完成需求草稿
- 角色：作为群内提问用户或需求反馈人
- 场景：当我想提交普通需求，但背景、截图、消息链接或期望效果还没整理完整
- 诉求：希望先保存为草稿，并看到哪些信息已保存、哪些信息还缺失
- 价值：以便后续补齐后再正式提交，减少遗漏和过早提交成本

- 诉求：希望草稿状态、正式提交动作、提交人、来源和缺失信息清晰可见

## 4. 功能需求

### F-01-1 创建需求草稿
- 所属故事：US-01、US-02
- 需求描述：用户或有权限运营人员可以将未整理完整的需求线索保存为“需求草稿”。
- 业务规则：草稿创建时应展示“草稿已保存，不代表正式提交”的明确提示；创建人应能看到草稿编号或可识别标题、当前状态、下一步补齐入口。
- 信息项：草稿至少支持保存标题、背景、期望效果、优先级建议、来源群/会话、来源消息引用、截图/附件、补充说明；缺失信息应标记为“待补充”，不得用系统猜测值冒充用户确认。
- 边界场景：标题为空、内容过短、附件读取失败、来源消息不可见、重复创建或频繁创建时，应给出可恢复提示；不得直接进入正式提交流程。
- 来源: modules/bot_api/send.go#L36-L48；来源: modules/bot_api/send.go#L53-L60；来源: modules/bot_api/send.go#L60-L70；来源: modules/bot_api/events.go#L37-L51

### F-01-2 草稿状态与正式需求单状态区分
- 所属故事：US-01、US-02、US-03
- 需求描述：草稿必须与正式需求单、PRD 草拟、Review、Accepted、Done 等流程状态区分展示。
- 业务规则：草稿可见状态至少包含“草稿中、待补充、可提交、已正式提交、已取消/已删除、已失效”；正式提交前不得展示为“已进入 PRD”“已接受”“已完成”。
- 边界场景：草稿被正式提交后，应展示对应正式需求单入口或编号；已取消、已删除、已失效草稿不得再次被误提交。

### F-01-3 草稿补齐、预览与正式提交
- 所属故事：US-01、US-02、US-03
- 需求描述：草稿创建后，创建人或有权限运营人员可以继续补充信息、预览正式提交内容，并在确认后正式提交。
- 业务规则：正式提交前应提示仍缺失的关键内容；提交动作应要求用户明确确认；正式提交后应展示成功结果、正式需求单入口和后续处理状态。
- 边界场景：必填信息仍缺失、优先级建议未确认、附件或消息链接已不可见、草稿已被他人更新、草稿已提交或已取消时，应阻止误提交并说明原因。

### F-01-4 附件、截图与消息链接处理

### F-01-5 权限与可见性边界
- 所属故事：US-02、US-03、US-04

### F-01-7 重复草稿与正式需求冲突提示
- 所属故事：US-01、US-02
- 需求描述：当用户创建或提交草稿时，系统应帮助识别明显重复的草稿或已存在正式需求，并提示用户确认是否继续。
- 业务规则：重复提示只能作为辅助判断，不替产品运营负责人做 duplicate、wontfix、invalid 等最终裁定；用户应能选择继续补充、合并线索或取消提交。
- 边界场景：仅标题相似、附件相同、消息来源相同或关键词相近时，不应自动关闭或覆盖现有需求；不应向无权限用户展示重复对象详情。

## 5. 状态与提示

- 草稿中：草稿已保存，但信息尚未齐全；不代表正式提交。
- 待补充：系统或运营人员识别出标题、背景、期望效果、优先级建议、截图/附件或消息来源存在缺口。
- 可提交：草稿已达到正式提交前的最小信息要求，等待用户或有权限运营人员确认。
- 已正式提交：草稿已转为正式需求单，并展示正式入口或编号。
- 已取消/已删除：草稿不再进入正式流程；如需继续需重新创建或恢复（若产品允许）。
- 已失效：草稿因超期、权限变化、来源不可见或材料失效，无法直接提交，需要重新确认。
- 无权限：当前操作者无权查看或操作该草稿、附件、来源消息或目标群；提示不得暴露无权对象是否存在。
- 附件/消息链接不可见：材料暂不可验证或当前无权查看，用户可重新上传、重新选择来源或补充文字说明。
- 疑似敏感信息：提示用户删除或脱敏后再保存/提交，必要时交由产品运营负责人或人工确认。

## 6. 验收标准

- AC-01：当群内反馈人信息未整理完整时，可以保存需求草稿，并看到“草稿已保存，不代表正式提交”的提示。
- AC-02：草稿能展示标题、背景、期望效果、优先级建议、截图/附件、来源消息链接或消息引用、补充说明的已填/待补充状态。
- AC-03：当草稿缺少关键内容时，用户能看到缺失项和下一步补充建议，系统不会把草稿误标为正式需求单。
- AC-04：当草稿达到最小信息要求时，用户或有权限运营人员可以预览正式提交内容，并在确认后正式提交。
- AC-05：正式提交成功后，用户能看到正式需求单入口或编号，以及后续处理状态；草稿状态同步展示为已正式提交。
- AC-06：草稿、正式需求单、PRD 草拟、Review、Accepted、Done 等状态在界面或提示中可区分，不产生误导。
- AC-07：当附件过大、格式不支持、下载地址过期、来源消息不可见或跨 Space 引用时，用户看到安全提示和补充建议，不泄露无权对象详情。
- AC-08：无权用户不能查看、编辑、提交、取消或删除不属于其权限范围的草稿，也不能通过草稿链接枚举群、Space、Bot、成员、附件或消息是否存在。
- AC-09：当草稿疑似重复正式需求或其他草稿时，系统只提示可能重复和可选动作，不自动做 duplicate、wontfix、invalid 或关闭裁定。
- AC-10：当触发创建频率、草稿数量、附件大小、正文长度或异常链接限制时，用户看到明确原因和可恢复建议。
- AC-11：草稿创建、编辑、提交、取消、删除和权限拒绝具备可追溯安全摘要，且不记录明文凭证、私密消息正文或无权对象详情。
- AC-12：产品说明覆盖适用范围、状态含义、正式提交条件、权限边界、附件/消息链接限制、过期策略、重复提示和安全脱敏要求。
- AC-13：需求管理专员只有在明确指派、草稿已正式进入 PRD 或产品运营负责人裁定进入 PRD 后，才基于草稿材料补 PRD；信息不足时最多提出 3 个关键待确认问题。

## 9. 五类风险检查

- 多租户 / Space 隔离：草稿、附件和消息链接必须按当前操作者有权 Space / 群 / 会话范围展示；跨 Space 或无权来源只能显示安全提示，不暴露对象是否存在。
- 权限 / ownership：创建、查看、编辑、提交、取消、删除草稿必须有明确操作者边界；产品运营负责人可在其有权范围内整理和提交，需求管理专员不得越权裁定正式状态。
- 安全 / 外部输入 / 凭证：草稿正文、截图、附件、链接可能包含敏感信息；疑似 token、cookie、secret、私钥或生产凭证必须脱敏提示，不进入公开 issue、群聊或日志。
- 限流 / 防滥用：草稿创建、补充、附件关联和列表查看需要频率、数量、大小、内容长度边界；异常高频或恶意链接不应影响正常需求流。
- 审计 / 可追溯：草稿从创建到正式提交的关键动作需要可追溯安全摘要，记录谁在何处对哪个草稿做了什么及结果，但不得记录明文敏感内容或无权对象详情。
