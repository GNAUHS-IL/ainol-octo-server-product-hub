# PRD：Bot API 与卡片发送失败原因用户可见化

## 1. 背景

运营同学在使用 Bot API 或卡片消息发送能力时，当前可能只能看到笼统失败，难以判断下一步应该补 Bot 群权限、确认频道是否存在、等待频控恢复、更新 token，还是联系负责人排查异常。

现有源码已经具备部分失败原因分类基础，例如 Bot 发送权限失败、群不存在、Bot 不在群内、群已解散、Space 成员关系不满足、认证失败、发送失败、限流维度等。但用户反馈表明，这些能力还需要统一成运营可理解、可区分、可安全展示的失败原因说明。

## 2. 目标用户

- 使用 Bot API 发送消息或卡片的运营同学。
- 负责配置 Bot 权限、群权限和频道目标的产品运营负责人。
- 需要排查 Bot API / 卡片消息失败的开发或支持人员。

## 3. 用户目标

用户希望在 Bot API 或卡片消息发送失败时，看到明确、可理解且安全的失败原因和下一步建议，能区分权限不足、目标不存在、被频控、token 失效、内部异常等场景，避免只能看到笼统失败。

## 4. 产品范围

### 本次包含

- 对 Bot API / 卡片消息发送失败原因进行用户可见分类。
- 至少覆盖以下用户可理解场景：Bot 没有群权限、频道/群不存在、群已解散、用户或 Bot 不在有权范围内、被频控/限流、token 失效或不可用、消息发送失败兜底。
- 每类失败原因必须给出下一步建议，例如补权限、检查目标、等待恢复、更新凭证或联系负责人。
- 对 token、权限、Space、内部异常等敏感场景做安全脱敏，不暴露可被枚举或滥用的信息。
- 同一类失败在 Bot API 与卡片消息发送场景下应尽量保持一致的用户理解口径。

### 本次不包含

- 不新增 Bot API 的业务能力。
- 不改变现有权限边界或认证规则。
- 不承诺所有内部异常都能外显为精确原因。
- 不展示内部服务、存储、队列、调用链或凭证明文。
- 不绕过限流、风控或权限限制。

## 5. 用户故事

作为使用 Bot API 或卡片消息能力的运营同学，我希望发送失败时能看到可区分的失败原因和下一步建议，以便判断应该补权限、检查目标、等待频控恢复、更新凭证，还是联系负责人处理。

## 6. 用户流程

1. 用户通过 Bot API 或卡片消息能力发送内容。
2. 发送失败。
3. 用户看到失败原因分类和下一步建议。
4. 用户根据提示执行可恢复动作：补群权限、确认目标、等待后重试、更新凭证或联系负责人。
5. 如果失败原因涉及敏感信息或内部异常，用户看到安全兜底提示，而不是内部细节。

## 7. 交互与文案要求

- Bot 无群权限：提示“Bot 当前无权向该群/频道发送，请确认 Bot 是否已加入并具备发送权限”。
- 频道或群不存在：提示“目标群/频道不存在或不可访问，请检查目标是否正确”。
- 群已解散：提示“目标群已不可用，请更换目标或联系负责人确认”。
- Space 或成员范围不满足：提示“当前账号或 Bot 不在可访问范围内，请联系负责人确认权限”。
- 被频控/限流：提示“当前请求过于频繁，请稍后重试；如持续出现，请联系负责人确认使用方式”。
- token 失效或不可用：提示“认证失败，请确认凭证是否正确或已更新”；不得说明 token 是否存在、归属或具体失效细节。
- 内部发送失败兜底：提示“消息暂未发送成功，请稍后重试或联系负责人排查”，不展示内部错误细节。

## 8. 验收标准

### 用户可见验收

- [ ] 当 Bot API 或卡片消息发送失败时，用户能看到失败原因分类，而不是只看到笼统失败。
- [ ] 当 Bot 没有群权限时，用户能看到权限相关提示和补权限建议。
- [ ] 当目标频道/群不存在或不可访问时，用户能看到检查目标的提示。
- [ ] 当触发频控/限流时，用户能看到稍后重试或联系负责人确认的建议。
- [ ] 当 token 失效或不可用时，用户能看到认证失败提示，但不会看到可用于枚举 token 的细节。

### 边界条件验收

- [ ] 当失败原因涉及 Space 隔离或成员关系时，提示不泄露其他 Space、群或用户是否存在。
- [ ] 当失败原因属于内部异常时，用户看到安全兜底提示和下一步建议。
- [ ] 当用户输入目标不完整或格式不符合要求时，用户能看到需要检查的目标信息类型。
- [ ] 同类失败在 Bot API 文本消息和卡片消息发送场景下口径一致。

### 安全与隐私验收

- [ ] 错误提示不展示 token、cookie、secret、私钥或任何凭证明文。
- [ ] 错误提示不暴露内部服务、存储、队列、调用链或敏感配置。
- [ ] 错误提示不帮助外部调用方枚举 token、Bot、群、频道或 Space 是否存在。
- [ ] 涉及权限、代用户发送、卡片审批或高风险操作时，应能追溯谁在什么范围内对什么对象执行了发送。

## 9. 非目标范围

- 本需求不改变 Bot 加群、授权、认证或限流的既有规则。
- 本需求不要求把所有底层异常完全精确展示给最终用户。
- 本需求不提供绕过频控、风控或权限限制的路径。
- 本需求不替代产品运营负责人对最终文案和优先级的确认。

## 10. 风险与待确认问题

1. 需要产品运营负责人确认哪些失败原因允许对外精确展示，哪些必须维持脱敏兜底。
2. 需要确认 Bot API 与卡片消息发送是否使用同一套用户可见失败文案。
3. 需要确认持续频控或疑似滥用时的运营处理入口。

## 11. 五类风险检查

- 多租户 / Space 隔离：失败提示不得让用户判断其他 Space、群、频道或 Bot 是否真实存在。
- 权限 / ownership：无权限、Bot 不在群、代用户发送等场景必须明确拒绝并给出合规下一步。
- 安全 / 外部输入 / 凭证：token 相关失败必须脱敏，不能区分到可被枚举或复用的细节。
- 限流 / 防滥用：频控提示应引导等待或联系负责人，不鼓励高频重试。
- 审计 / 可追溯：涉及发送失败、权限拒绝、代用户发送或卡片交互时，应能追溯操作者、目标范围和处理结果。
