# PRD：补充认证入口与鉴权方式说明

## 1. 背景

用户和运营同学需要快速判断 Octo 中不同认证入口分别适用于哪些场景：普通用户登录态、Bot API 调用、Bot 验证、daemon API Key 验证等。如果缺少统一说明，排查“登录成功但后续访问失败”“Bot token 与用户 token 混用”“API Key 绑定关系不清”等问题时容易误判。

现有源码中已经存在用户 token 解析、标准 Bearer 兼容、Bot token 前缀区分、认证验证入口等能力基础，因此本需求聚焦于形成用户和运营可读的认证入口说明材料，而不是改变认证实现。

## 2. 目标用户

- 需要接入或排查 Octo API 的开发/运营同学。
- 负责 Bot API、BotFather、daemon API Key 接入说明的产品运营负责人。
- 需要判断认证失败归因的需求管理与 Review 人员。

## 3. 用户目标

用户希望看到一份清晰、可引用的认证入口说明，能判断自己应该使用哪类凭证、在哪类场景使用、失败时应优先检查什么，并避免把不同认证方式混用。

## 4. 产品范围

### 本次包含

- 补充用户登录态、Bot API token、Bot 验证、daemon API Key 验证的适用场景说明。
- 明确不同凭证不可混用的用户可见规则。
- 明确认证失败时的运营排查顺序，例如先确认凭证类型、使用场景、绑定对象、所属 Space 或 Bot 是否仍有效。
- 对涉及凭证的说明采用脱敏表达，不展示 token、cookie、私钥或生产密钥。
- 说明材料必须能被 issue、PRD、Review Gate 引用。

### 本次不包含

- 不新增认证方式。
- 不改变现有登录、Bot API、BotFather 或 daemon 的权限边界。
- 不承诺暴露内部诊断细节。
- 不包含具体实现方案、存储设计或内部字段设计。

## 5. 用户故事

作为接入 Octo 能力的运营或开发同学，我希望能看到不同认证入口的适用范围和失败排查说明，以便在认证失败时判断是凭证类型错误、使用场景错误、绑定关系失效还是需要联系负责人确认权限。

## 6. 用户流程

1. 用户遇到认证、鉴权或 Bot API 接入问题。
2. 用户进入认证入口说明材料。
3. 用户根据场景选择对应说明：普通用户登录态、Bot API token、Bot 验证、daemon API Key 验证。
4. 用户查看该凭证适用范围、不可混用规则和失败排查建议。
5. 用户根据说明重试、补充信息或联系产品运营负责人确认权限/绑定关系。

## 7. 交互与文案要求

- 成功理解时：用户能明确知道当前场景应使用哪类认证入口。
- 失败排查时：提示用户优先确认凭证类型、使用场景、绑定对象和权限范围。
- 信息不足时：最多列出 3 个需要补充的信息：使用场景、凭证类型、目标对象。
- 无权限时：提示用户联系有权负责人确认权限或绑定关系，不暗示可以绕过权限。
- 安全提示：所有凭证示例必须脱敏，不展示真实 token、cookie、secret 或私钥。

## 8. 验收标准

### 用户可见验收

- [ ] 用户能在说明材料中区分普通用户登录态、Bot API token、Bot 验证和 daemon API Key 验证的适用场景。
- [ ] 用户能看到不同认证方式不可混用的明确提示。
- [ ] 用户遇到认证失败时，能看到可执行的排查建议。
- [ ] 说明材料可被 issue、PRD 和 Review Gate 引用。

### 边界条件验收

- [ ] 当用户无法判断凭证类型时，说明材料能提示需要补充哪些信息。
- [ ] 当用户无权访问目标对象时，说明材料提示联系负责人确认权限，不暴露目标对象的敏感细节。
- [ ] 当涉及 Space 或 Bot 绑定关系时，说明材料强调只能在有权范围内确认。

### 安全与隐私验收

- [ ] 说明材料不展示真实 token、cookie、secret、私钥或生产凭证。
- [ ] 说明材料不鼓励绕过认证、伪造身份或扩大权限范围。
- [ ] 说明材料只表达用户/运营可理解的产品规则，不暴露内部敏感细节。

## 9. 非目标范围

- 本需求不定义新的认证协议。
- 本需求不改变现有权限校验结果。
- 本需求不替代产品运营负责人对最终入口口径的确认。
- 本需求不覆盖所有第三方集成文档。

## 10. 风险与待确认问题

1. 需要产品运营负责人确认说明材料最终放置位置与对外可见范围。
2. 需要确认是否把“daemon API Key”作为外部可读术语，还是改为更面向运营的名称。
3. 需要确认无权限或绑定失效时的联系人/处理入口。

## 11. 五类风险检查

- 多租户 / Space 隔离：说明材料必须强调用户只能确认自己有权 Space 或 Bot 范围内的信息。
- 权限 / ownership：涉及 Bot 或 API Key 归属时，只提示联系有权负责人确认，不展示他人归属细节。
- 安全 / 外部输入 / 凭证：所有凭证示例必须脱敏，不展示真实 token、cookie、secret 或私钥。
- 限流 / 防滥用：认证失败排查说明不得鼓励高频重试；应提示按产品提示等待或联系负责人。
- 审计 / 可追溯：涉及权限确认、绑定关系确认时，应能追溯由谁确认、确认对象和处理结果。

## 12. 证据

- API 服务启动时已注入用户 token 解析相关能力。来源: main.go#L205-L214
- 标准 `Authorization: Bearer` 可兼容普通用户登录态调用。来源: main.go#L279-L288
- Bot API 会按 token 前缀区分 App Bot 与 User Bot。来源: modules/bot_api/auth.go#L25-L34
- 用户 token、Bot 验证、daemon API Key 验证存在公开的验证入口分组。来源: modules/user/api.go#L403-L407
- Bot 验证入口返回 Bot 与归属相关的用户可理解信息。来源: modules/user/api.go#L4960-L4973
