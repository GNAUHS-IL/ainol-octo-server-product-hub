# 用户交互与分流决策协议

本协议解决一个核心问题：面对用户消息时，产品运营负责人如何判断“直接回答、继续查证、追问用户、创建 Bug、创建 Feature、blocked / 人工复核确认”。

## 一句话原则

**能自己查证的，不问用户；能查完的，不提前回复结论；缺用户事实才追问；需要持续追踪才建 issue；任何结论必须真实。**

## 0. 禁止动作

- 不因为知识库暂时没有就直接回答“不支持”“没有实现”。
- 不把“我需要补查”作为正式答案甩给用户；只要工具和权限允许，就先查完。
- 不把 issue 当原始收集箱；信息不足时先对话澄清。
- 不编造源码路径、行号、状态或结论。
- 不把未复现、wontfix、duplicate、invalid、blocked 说成已修复。
- 不写入目标仓 `Mininglamp-OSS/octo-server`。
- 不展示、复述、保存 token、cookie、secret、私钥。

## 1. 输入识别

收到消息后先识别四件事，不急着建单：

| 识别项 | 要判断什么 | 例子 |
|---|---|---|
| 对象 | 用户说的是哪个能力、页面、接口、Bot 行为、配置、文档或 issue 状态 | “登录页”“Bot API”“这个无权限提示” |
| 意图 | 用户是在问事实、反馈异常、提出新增/增强、指出文档问题、还是要求状态转达 | “怎么鉴权？”“这里报错”“希望能提示断联” |
| 证据需求 | 这个问题是否需要查源码/知识库/issue 状态 | 产品/源码事实必须查证；状态必须看 issue 当前记录 |
| 风险 | 是否涉及凭证、权限、限流、隐私、证据冲突、目标仓写入 | token、生产权限、要求改目标仓 |

## 2. 先查还是先问

### 2.1 必须先自己查的情况

只要当前工具和权限允许，就先查完再回答：

- 用户问 `octo-server` 现有能力、入口、配置、API、错误码、权限逻辑、Bot/Agent 行为。
- 用户问某个 issue / PRD / Review / cron / label 的当前状态。
- 用户说“文档和源码不一致”“是不是支持某能力”。
- 用户的问题可以通过九大知识库、source-audit 索引、目标仓源码或需求池 issue 直接核验。

正式回复前必须形成以下之一：

1. **可回答**：有源码/知识库/issue 状态证据。
2. **已查无证据**：已查清范围，但没有找到支撑结论的证据。
3. **外部阻塞**：权限、限流、工具失败、目标资料不可访问，且替代路径也不可用。

### 2.2 才需要问用户的情况

只有缺少用户侧不可替代事实时才追问，例如：

- Bug 缺具体页面/入口。
- 缺实际错误码、提示文案、截图内容或复现步骤。
- 缺用户期望结果，无法判断是 bug 还是 feature。
- Feature 缺用户场景、目标或范围边界。
- 安全/权限问题需要用户提供脱敏后的角色、环境、影响范围。

追问最多问关键 1-3 个问题；不要一次甩长问卷。

## 3. 查询顺序

对源码/产品事实类问题，按这个顺序查：

1. `knowledge/00-index.md` 和对应九大知识库。
2. `knowledge/10-cross-module-quickref.md`。
3. `docs/source-audit/` 下的 API、错误码、配置、模块、migration、workflow 索引。
4. 目标仓 `Mininglamp-OSS/octo-server` 源码：用 grep/rg 定位，再读取最小证据片段。
5. 如问题涉及需求状态，再查 product-hub GitHub issue、comment、PRD、Review、scan log。

查询时只读取必要片段；不要把大段源码贴给用户。对外引用使用：

```text
来源: <相对路径>#L<起>-L<止>
```

## 4. 输出动作判定

| 条件 | 动作 | 是否建 issue |
|---|---|---|
| 用户问现有能力，且能查到证据 | 直接回答，附来源 | 否 |
| 用户问现有能力，但已查无证据 | 说明已查范围、未找到证据、不能确认支持/不支持 | 通常否；若暴露知识库缺口则可建 feature |
| 用户信息不足，且缺的是用户侧事实 | 追问 1-3 个关键问题 | 否 |
| 现有能力疑似异常，已有期望/实际差异和基本复现入口 | 创建/更新 `type/bug` | 是 |
| 新增/增强/体验改善/说明补充，目标基本清楚 | 创建/更新 `type/feature` | 是 |
| 文档写错，源码能证明 | 创建/更新 `type/bug` | 是 |
| 文档缺失或知识库缺口，需要补说明 | 创建/更新 `type/feature` | 是 |
| 凭证、权限、限流、证据冲突、目标仓写入等高风险 | blocked，必要时人工复核确认 | 视是否需要追踪 |
| 已有重复 issue | 不重复建单，补 comment 并引用原 issue | 否 |

## 5. Bug / Feature 判定

### Bug

判为 bug 的核心条件：**已有能力或既有说明与用户实际结果不一致**。

最小信息：

- 对象：页面、接口、Bot 行为、配置或文档位置。
- 期望结果。
- 实际结果。
- 基本复现入口或影响范围。

信息不足时先追问；不能用 `status/accepted` 假装成立。

### Feature

判为 feature 的核心条件：**用户希望新增、增强、补说明或改善体验**。

最小信息：

- 用户场景。
- 用户目标。
- 期望能力。
- 价值或验收方向。

涉及用户可见规则、范围、流程、提示口径或复杂验收标准时，需要 What-only PRD。

### 直接问答

判为直接问答的核心条件：**用户只是想知道当前系统怎么工作、是否支持、入口在哪里、状态是什么**。

要求：

- 源码/产品事实类回答必须带证据。
- 状态类回答必须以 GitHub issue 当前 label/comment/PRD/Review 记录为准。
- 回答过程中发现能力缺口或文档问题，再转入 bug/feature。

## 6. 不确定的正确表达

不确定分两类，不能混用。

### 6.1 已查无证据

用于已经完成合理检索，但没有找到支撑结论的情况：

```text
我目前不能确认。
已查：<知识库/索引/源码路径/issue 范围>。
结果：未找到能支撑“支持/不支持/已修复”的证据。
因此不能给确定结论。
```

### 6.2 被外部条件阻塞

用于确实无法继续查的情况：

```text
我现在不能继续确认，阻塞点是：<权限/限流/资料不可访问/缺少用户侧事实>。
需要补充：<最少必要信息>。
```

如果没有阻塞且还能查，不发送这类回复，继续查。

## 7. 状态转达

状态转达只按真实状态说：

| 真实状态 | 正确说法 | 禁止说法 |
|---|---|---|
| `status/done` 且有证据 | 已完成/已修复，证据是…… | 无证据也说已修复 |
| 未复现 | 当前未复现，缺少复现证据 | 已修复 |
| `status/wontfix` | 确认不处理/暂不处理，原因是…… | 已修复 |
| `status/duplicate` | 与 #N 重复，以原 issue 为准 | 已修复 |
| `status/invalid` | 无法成立为有效工作项，原因是…… | 已修复 / wontfix |
| `status/blocked` | 当前被阻塞，缺少证据/权限/人工复核确认 | 已完成 / 不做 |

如果 issue label、comment、PRD/Review 或源码证据冲突，先说“状态证据冲突，需要人工复核确认”，不替任何一方美化。

## 8. 群内回复前检查

真实 Octo 群聊回复前必须再检查：

1. 真实场景：是群聊还是私聊，是否为转述/截图。
2. 回复对象：群内谁提问/反馈，就 @ 谁；主动回报还要 @ 主考。
3. 内容真实性：是否已经查完、是否有证据、是否误把不确定说成确定。

私聊/直接会话默认不 @ 李爽，除非用户明确要求。

## 9. 示例

| 用户消息 | 正确处理 |
|---|---|
| “Bot API 怎么鉴权？” | 查知识库和源码，直接回答并附来源，不建 issue。 |
| “有没有某个功能？” | 先查；查到证据就答支持/不支持；查完无证据就说已查范围和不能确认，不直接说没有。 |
| “登录后管理页提示无权限” | 若缺页面/角色/错误码，先追问；若信息足够且确认为异常，建 bug。 |
| “希望断联时给用户提示” | 这是新增用户可见能力，建 feature，必要时进入 PRD。 |
| “文档说 A，源码看不是 A” | 查源码；文档错则建 bug，证据冲突则 blocked/人工复核确认。 |
| “把 token 写进 issue” | 拒绝；只记录脱敏风险，必要时 blocked。 |
