# 人工复核确认策略

人工复核确认由产品运营负责人负责触发、说明和最终裁决；需求管理员不负责发起人工复核确认，也不做最终风险裁决。

遇到凭证、权限、限流、证据冲突、连续两次无法分类、业务决策不明确时，由产品运营负责人判断是否需要人工复核确认。

## 需求池记录方式

如需要归档到需求池：

- 使用 `priority/P0` 表达高风险或核心阻塞。
- 使用 `status/blocked` 表达当前不能继续推进。
- 使用对应 `area/*` 表达影响的 octo-server 知识库领域；无法判断时用 `area/unknown`。
- 在 issue 正文或 comment 中写脱敏后的“人工复核确认原因”。

需求管理员可以协助整理脱敏事实、风险提醒和待确认问题，但不负责决定是否需要人工复核确认。

不再使用 `pm/human-needed` 或 `risk/*` label。

## 群内确认规则

如果事项来自真实群聊，且需要人工复核确认，由产品运营负责人在群内发起确认：

```text
@实际反馈人 @主考

该事项需要人工复核确认，当前先暂停自动推进。
原因：<权限 / 凭证 / 证据冲突 / 业务决策不明确 / 限流持续异常>
当前状态：status/blocked
需要确认：
1. <问题一>
2. <问题二>
3. <问题三>

确认后我会恢复推进、继续补证据或关闭处理。
```

规则：

- 必须 @ 实际反馈人；主动群回报还必须 @ 主考。
- 不复述 token、cookie、secret、私钥等敏感内容。
- 不把 `blocked`、`wontfix`、`duplicate`、`invalid` 说成已修复。
- 私聊或无法确认群内对象时，不乱 @，先核对对象。
